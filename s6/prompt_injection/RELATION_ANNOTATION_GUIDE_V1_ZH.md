# 关系抽取标注指南 v1

来源：[`ANNOTATION_CONSISTENCY_AUDIT_V1_ZH.md`](ANNOTATION_CONSISTENCY_AUDIT_V1_ZH.md)
发现的三条规范边界，经用户确认后写成本指南。本指南**只是把既有冻结参考
（`relation_scale_targets_v1.py` 等）里一直隐含遵守的规则写成明文**，不改变
任何已确认的人工语义标签，也不修改 `relation_contract_v2.py` 的校验逻辑/
`ROLES`/`STATES`枚举或任何冻结训练数据与评估结果。下次如果有新的标注、
few-shot 示例或重训获批，应参照本指南；在此之前，本指南是文档，不是代码，
不改变任何现有产物或哈希。

## 规则 1：传递类动词的内容 payload 用 `data`，非传递实体用 `object`

当动作的语义是把某个内容/数据本身进行传递（导出、发送、写入、显示……的直接
宾语是"被移动/被给出的内容"）时，承载该内容的绑定角色标 `data`；`object` 只
用于被直接操作、但本身不发生位置/归属转移的实体（表名、文件名、密钥、记录
本身等）。

判断口诀：问"这是动作作用的对象，还是动作传递/产出的内容"？前者 `object`，
后者 `data`。

对照例子（均来自已冻结参考，`relation_scale_targets_v1.py`）：

| 场景 | 文本 | 正确角色 | 说明 |
|---|---|---|---|
| 导出列 | "item_id 和 count 两列" | `data` | 导出的是列内容本身 |
| 导出列 | "测试表" | `object`（经 `source` 更准确） | 被查询/读取的表，不是被传递的内容 |
| 发送报告 | "合成报告" | `data` | 被发送的内容 |
| 发送报告 | "demo-a" | `destination` | 接收方，不是内容也不是被操作实体 |
| 删除日志 | "日志" | `object` | 被删除的实体本身，没有被传递给第三方 |

容易出错的信号：动词是"导出/发/发送/写入/传给/抄送"这一类，且后面紧跟的是
具体列名/文件内容/报告/消息等"信息载荷"，而不是设备、账户、表、文件等"被操
作实体"。

## 规则 2："保留 / 不变"类负面约束进 `constraints`，不进 `actions`

当材料里出现"其他 X 保留""其他 Y 不动""除此之外不要改动……"这类负面保留
从句，且该从句**不是**一个独立的、以显式动词开头的禁止性指令（例如"不得抄送
给任何人"这种本身就该是一个 `kind="prohibited"` 的 action），而是对操作范围
的一句补充说明，就把这句话原样放进顶层 `constraints` 数组，不要拆成一个独立
的 `action`。

对照例子：

| 场景 | 原文从句 | 正确位置 |
|---|---|---|
| 清理日志 | "其他文件保留" | `constraints: ["其他文件保留"]` |
| 按租户更新 | "其他租户记录不动" | `constraints: ["其他租户记录不动"]` |
| 发送报告 | "不能增加其他收件人" | 独立 `action`（`kind="prohibited"`），**不是** constraints |

区分标准：如果这句话本身是一个"不要做 X"的完整动词短语，建成独立的
prohibited action；如果它是对前面那个动作的作用范围做补充限定（"只……，其他
……保留/不动"里"其他……"那半句），放 constraints。

**训练提醒**：本次审计发现模型在 6/6 个"保留类约束"案例里全部误转成了多余
的 action，而 few-shot/训练示例目前没有覆盖"进 constraints 而非 actions"的
正例。如果未来重训或扩充 few-shot，必须至少补一条这样的例子，否则这条规则
写了也不会生效。

## 规则 3：`unmapped` 只用于"文本本身无法指向具体对象"，不因关联的其他不确定性而标

一个绑定的 `status` 标 `unmapped`，当且仅当**这段文本自身**无法对应到一个具
体、可执行的真实对象或值（比如"某个分区"但不知道对应哪个键前缀，"某个租户"
但不知道对应哪个 tenant_id）。如果不确定性其实属于**另一个独立实体**或**另
一个维度**，应该：

- 要么由另一个独立绑定自己标 `unmapped`（而不是牵连当前绑定）；
- 要么放进 `missing_context`，而当前绑定本身保持 `explicit`。

同一条输出里，如果某个绑定写了 `status="unmapped"`，一般应该能在
`missing_context` 里找到对应说明该绑定为何无法解析；反过来，`missing_context`
里提到的某个概念不对应任何映射，不代表提到该概念的**所有**绑定都要标
`unmapped`——要具体看哪个绑定承载了那个无法解析的部分。

对照例子：

| 场景 | 文本 | 正确 status | 原因 |
|---|---|---|---|
| 清理缓存分区 | "演示缓存分区"（`object`） | `unmapped` | 这段文本本身没有对应到具体键前缀，且 missing_context 说明了同一件事 |
| 删除旧日志 | "旧日志"（`object`） | `explicit` | 文本本身明确指代"日志"这个对象；"旧"这个模糊修饰词由另一个独立的 `parameter` 绑定单独标 `unmapped` |
| 按租户更新 | "当前租户记录"（`object`） | `explicit` | 对象本身明确；真正无法解析的是"当前租户"对应哪个 tenant_id，由独立的 `actor` 绑定标 `unmapped` |
| 运行宏 | "试验宏"（`object`） | `explicit` | 宏名称本身是明确的，不确定的是宏定义细节，放 `missing_context`，不影响这个绑定 |

容易出错的信号：看到材料里有"某个 XX""具体 YY 未说明"这类措辞就把当前这个
绑定整体标成 `unmapped`，而不去检查"不确定的到底是哪一小块信息、该由哪个绑
定承担"。

## 使用方式

本指南用于：
1. 未来人工标注新核心材料时的参考口径（避免审核者之间口径不一致）。
2. 未来如果重训/扩充 few-shot，示例选取和 prompt 撰写时对照本指南补齐覆盖面
   （尤其规则 2 当前完全没有被覆盖）。

本指南**不**用于：
1. 重新评判 102 个已确认核心材料的语义标签——它们的审核结果不变。
2. 原位修改 `relation_contract_v2.py`/`relation_scale_targets_v1.py` 或任何
   已冻结的训练/评估数据与已发布的指标。
3. 作为新训练或新评估已经发生的依据——是否以及何时据此重训，由后续新一轮
   讨论的明确需求决定。
