# 独立代码来源上的提示词注入检测（探索性）

200 个 Python 标准库代码文件，各取一个函数片段；按源文件分为开发 100、测试 100。每个来源有 1 条干净记录、2 条手工模板注入变体（注释前置和后置）。开发与测试使用不同注入措辞。所有来源、模板和划分在评分前冻结。

|---|---|---:|---:|---:|---:|

| development | supervised | 2.00% | 1.00% | 4/196 | 1/99 |
| development | union | 5.00% | 4.00% | 10/190 | 4/96 |

测试集规则与监督分类器共同漏检：176/200 条攻击变体。
并集仅作离线参考，不参与工具授权；不能因为检出提高而忽略误报。

## 误差诊断

来源审计确认：200 个文件均不在 `site-packages`／`dist-packages`，与 BIPIA 原始正文的标准化完全匹配数为 0。测试集的 100 条干净代码每误报 1 条即增加 1 个百分点，监督分类器的 0/100 不代表真实误报率为零。

原始标准库片段保留在本地、未纳入 Git；仓库保存生成脚本、Python 版本与数据哈希。同版本同来源环境可用 `prepare` 模式重建，重建内容必须与冻结协议完全匹配才会写入。预测 CSV 不包含代码正文。

测试集监督分类器的 16 条检出全部集中在 1/4 种注入措辞上，其余 3 种措辞均未检出；前置和后置各 8 条。规则检测的 4 条干净误报来自 `urllib.parse`、`enum`、`xml.etree.ElementTree` 与 `getpass` 的正常代码，理由是“高风险语言”或“独立指令式文本”。这说明新来源上的主要问题是泛化与代码语境识别，而非单纯调低阈值。

本轮没有依据测试集错误修改 P1 或监督分类器，也没有改变工具授权。下一次方法实验应先在开发来源提出代码注释／文档字符串的任务重定向信号，并另留新的来源做确认；当前测试集已被查看，只能继续用作探索性分析。

## 边界

这是合成注释注入的检测指标，不是真实代理攻击成功率；代码来源限于 Python 标准库，任务描述为统一的通用修复任务，两个攻击变体共享同一来源，不能当作独立样本。不同于 BIPIA Code，本实验既更换了代码来源，也更换了攻击模板，指标不可直接混成同一个平均值。
