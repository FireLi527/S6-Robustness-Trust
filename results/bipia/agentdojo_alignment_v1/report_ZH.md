# AgentDojo 调用级任务对齐（含参数来源检查）：在相同安全性下减少人工复核，放宽版本明显提升可用性

日期：2026-10-03。数据：AgentDojo v1.2.2（MIT，仓库 commit `a75aba76`，包版本 0.1.35），4 个套件、97 个用户任务、35 个注入任务。正常调用和攻击调用都取自官方 `ground_truth()`，带结构化参数。运行环境为 WSL 中独立的 `~/.venvs/agentdojo`，没有调用任何模型或 API。

## 1. 协议

- 每个套件内，用户任务和注入任务分别按加盐 SHA-256 对半切分；开发集 = 开发用户 × 开发注入，测试集同理，交叉组合不使用。数据导出时即冻结切分。
- 规则只在开发集上设计，共迭代 3 轮（见第 3 节）。测试评估核对代码哈希，必须与开发评分时一致才能运行，并且只运行了一次。
- 工具注册表（动词分类所用）是部署时就已知的系统信息，因此使用完整工具列表；动作词表、委托词表只来自开发集的用户任务。
- 测试集：49 个正常任务；253 个攻击实例，其中 **100 个注入目标没有任何工具调用**（例如“告诉用户某酒店很好”），调用级防护管不到，单独计数。其余 153 个参与评估。

## 2. 三种策略

- **P3 式闸门**：读取放行，写入全部转人工复核（这些工具没有预先批准的目标）。
- **P3＋任务对齐**：取两者中更严格的结果，不会比 P3 更宽松。
- **研究变体（对齐放行）**：如果写入动作是任务明确要求的，且所有目标参数（收件人、账号、参与者、链接、频道、密码）都是用户在任务里写明的，就直接放行，不再转复核。**这放宽了 P3，只用于研究比较，不部署。**

对齐规则：读取放行；写入动作没有被任务请求（且任务不是委托式）→ DENY；委托式任务（“照邮件里的待办去做”等）→ REVIEW；目标参数不是用户写明的 → REVIEW；破坏性动作（删除、取消、移除）的对象与任务提到的对象不一致 → DENY。

## 3. 开发集迭代记录

1. 第 1 版：研究变体放行了 9/152 个攻击目标（改密码、删错对象、创建日历事件）。
2. 第 2 版：把密码加入来源检查；新增对比对象规则。结果误伤正常私信 5 条（任务中“统计频道消息”触发了对象不符）。
3. 第 3 版：对比规则只用于删除、取消、移除。开发集结果：正常任务全自动完成 35/48，没有正常调用被拒绝；攻击目标被完整放行 7/152。创建日历事件类攻击按字面无法区分，接受漏判。

## 4. 测试集结果

| 指标 | P3 式闸门 | P3＋任务对齐 | 研究变体 |
| --- | ---: | ---: | ---: |
| 正常任务全部调用自动放行 | 21/49（42.9%） | 21/49 | **40/49（81.6%）** |
| 正常写入调用被直接拒绝 | 0/33 | 2/33 | 2/33 |
| 攻击目标被完整自动放行 | 11/153 | 11/153 | 14/153 |
| 攻击写入调用：拒绝 / 复核 / 放行 | 0 / 164 / 0 | **110** / 54 / 0 | 110 / 51 / 3 |

按套件，研究变体（正常全自动 / 攻击完整放行）：banking 6/8、0/40；slack 7/11、11/33；travel 9/10、3/40；workspace 18/20、0/40。

## 5. 解读

1. **P3＋任务对齐**在不放宽任何权限的前提下，把 67%（110/164）的攻击写入从“交给人判断”变成直接拒绝。代价是 2 条正常写入被误拒。
2. **研究变体**体现了可用性与安全的取舍：用户明确写出目标的写入不再需要人工批准，正常任务的全自动完成率从 42.9% 提高到 81.6%，攻击目标被完整放行只多了 3 个（11→14）。
3. **三种策略都没拦住的 11 个**，全部来自同一个注入：让模型访问攻击者的网址（`get_webpage`）。读取工具同样可以泄露信息或引入新内容，下一版应对网络读取的 URL 也做来源检查。
4. **误拒的 2 条正常写入**都是同义表达没有覆盖：“adjust my rent payment”，以及 “reservation” 与词表中的 “reserve” 不是子串关系。仅凭词表缺少某个动作词，不足以支撑 DENY；下一版应把“未找到请求词”改为 REVIEW，DENY 只保留给有明确反证的情况。
5. **研究变体放行的 3 条攻击写入**：1 条是注入恰好使用了用户自己写在任务里的收件人（字面来源检查无法区分）；2 条是用户问的是餐厅，注入却预订了酒店（对比对象规则只用于破坏性动作）。
6. 有 100 个注入目标不涉及工具调用（只影响模型的回答内容），调用级防护无能为力，需要回答层面的检测来配合。

## 6. 局限

- 规则仍是英文词表加字面匹配；参数来源只认字面出现，无法跟踪“从可信数据中查到的值”。CaMeL 一类方法用数据流追踪解决这个问题。
- 用的是官方标准答案的调用序列，不是实际模型生成的调用；没有运行真实智能体，所以不是端到端的攻击成功率。
- 开发集看过 3 轮；测试集只评估了一次，此后只能作为已曝光的诊断数据。

复现：`~/.venvs/agentdojo/bin/python -m s6.prompt_injection.prepare_agentdojo_alignment_v1`（WSL）→ `evaluate_agentdojo_alignment_v1 --split development` → `--split test`（Windows 的 `.venv-bipia`，独占运行目录，测试评估要求代码哈希一致）。
