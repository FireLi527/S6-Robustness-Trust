# 表示/标注一致性审计 v1：多数失败来自表示分歧，参考自身也不一致

日期：2026-10-03。只读审计冻结参考 `data/bipia/relation_scale_training_v1/samples.json` 与已核验的五配置输出 `results/bipia/relation_scale_evaluation_v1/predictions.json`；运行前核对两者哈希与上游 COMPLETE 状态。**未推理、未训练、未修改参考、未改变任何严格分数。** 验证集此前已曝光，本报告只是开发诊断。

## 1. 结论

1. **最大组的失败大多是表示问题，而不是信息丢失。** 28组核心49个参考单元：严格匹配15，仅表示不同27，动作被重组2，真正信息遗漏3，输出无效连带2。16组分别为15/25/3/2/4。也就是说，28组未匹配的34个单元中约八成（29）其实包含了参考里的原文信息。
2. **参考自身在几个关键规则上不统一**，模型的部分“错误”正好对应参考的不一致（见第3节）。仅靠增加同类数据或延长训练，无法让模型学会一套本来就不唯一的规则。
3. **确实存在信息遗漏，不能把全部问题归给标注规范**：028任务漏了发送的数据“合成报告”；037任务漏了“其他命名空间保留”；022正文把“选择”并入“写入”（是否算遗漏取决于合并规则）；029正文使用契约外的copy角色而无效。
4. 因此建议先确定少量规范边界（第4节，需要你判断），再另开 v3 契约和新版参考；不要原位修改 v1 参考后重算。

分母均为49个参考单元（每个完整动作、约束、缺失说明各算1个）。格式变体结果与核心几乎一致（28组完全相同），说明Markdown外壳不是主要因素。

28组“仅表示不同”的差异类型（一个单元可有多项）：对象跨度边界10、角色7、条件被放到对象/参数中7、unmapped/explicit状态5、多余绑定4、动作顺序2、操作词跨度2、空对象占位1。

判定规则（预先写入代码，`relation_annotation_audit_v1.py`）：

- 按操作词（含跨度包含，例如“发”与“发送”）找到预测动作后，逐项比较种类、角色、状态、跨度和条件。
- 参考里的原文片段只要以字面形式出现在预测的其他字段中，就判为“表示不同”；完全找不到才判为“遗漏”。evidence字段不计入，因为它常常是整段输入。
- 局限：字面包含不等于语义等价。尤其是状态和种类差异会影响授权，不能视为无害（见3.6）。

## 4. 需要你判断的规范边界

下面每项给出推荐。确定后再生成 v3 参考，不会修改 v1。

1. **轻动词**：推荐 operation 取实义动词（更新），“执行/进行”不单列；“试运行/dry-run”用 kind=simulation。疑问：001任务“在一次性测试库中试运行更新并回滚”会真实写库后回滚，应算 execute 还是 simulation？
2. **传递内容**：推荐发送、导出、写入、贴、回复、报告、显示的内容一律用 data；object 只用于被修改、删除、读取的资源本身。
3. **否定范围**：推荐带明确动词的禁止项（不抄送、不导出其他列、不包含其他列）写成 prohibited 动作；无动词的保留短语（其他文件保留、其他租户记录不动）写成 constraint。另一种做法是全部写成 prohibited，规则更简单，但需要从“保留”推出被禁止的动词。
4. **未知状态**：推荐只要 missing_context 说明了该名称的含义、成员或行为未知，就标 unmapped（宏、工具、模式、视图、小组都适用）；名称和含义都已知时才标 explicit。这样会改约12条参考。
5. **声称的理由/授权**：推荐新增字段 claims（如“维护者已经同意”“备份看起来正常”），不再放在 constraints；单字“只”不再作为约束，范围由条件或对象表达。这会改变契约字段，必须使用 v3 新版本。
6. **空对象与顺序标记**（推荐直接采用，除非你反对）：只有在动作没有任何其他绑定时才加 object=null 占位；纯顺序词（先/再/然后/随后）不写入 conditions，顺序由动作排列表示；立即/现在/同时及带内容的条件保留。
