# 调用级任务对齐 v1：越权读取几乎全部拦下，代价是正常调用的摩擦增加

日期：2026-10-03。问题：一个拟执行的结构化工具调用，是否服务于可信的用户任务？方法是确定性规则，不调用模型，也不读取正文。最终决定取“P3 式权限闸门”和“任务对齐”两者中更严格的一个，因此不会比 P3 更宽松，也不授予任何权限。

## 1. 数据与协议

- 来源：InjecAgent base（MIT），本地冻结副本，哈希按 manifest 核对。数据不是本项目编写的。
- **按两个维度切分，在设计任何规则之前冻结**：17 个用户案例分为开发 8 / 测试 9；攻击指令在 dh、ds 两类中各对半分。开发集 = 开发用户 × 开发攻击，测试集 = 测试用户 × 测试攻击，交叉组合不使用。所以测试集里的用户任务和攻击指令在设计规则时都没有出现过。
- 规则只在开发集上设计，**只写了一版，没有迭代**。测试评估会核对代码哈希，必须与开发评分时完全一致才能运行，并且只运行了一次。
- **需要如实说明**：切分之前，为了解数据格式，我打印并看过全部 17 个用户任务，其中包括测试集的 9 个。当时还没有设计规则，服务别名表也只来自开发集；测试集上因此出现的错误都原样保留。

## 2. 方法

1. 拆分工具名的驼峰词，第一个已知动词之前是服务，动词决定动作类别：读取或写入/发送。动词表只来自开发集工具名，不认识的动词标为“未知”。
2. 任务对齐：任务文本中提到了服务名，或提到了开发集确认过的别名（如 email→Gmail），就算服务一致。
3. 判定：服务一致且为读取，或服务一致且写入是任务明确要求的，判 ALLOW；服务一致但写入未被要求，判 DENY；服务不一致的读取，判 REVIEW；服务不一致的写入，判 DENY；动作未知，判 REVIEW。
4. 对照组“P3 式闸门”：读取直接放行，其他动作转人工复核。这里依赖同一个动词表来识别读取；真正的 P3 注册表里没有这些工具，会全部拒绝，包括正常调用，所以用这个更公平的版本来对比。

## 3. 测试集结果（9 条正常调用，423 条攻击调用，279 条攻击链）

| 指标 | P3 式闸门 | P3＋任务对齐 |
| --- | ---: | ---: |
| 正常调用自动放行 | 9/9 | **6/9** |
| 攻击调用自动放行 | 126/423（29.8%） | **1/423（0.24%）** |
| 攻击调用直接拒绝 | 0/423 | **198/423（46.8%）** |
| 留给人工复核的攻击调用 | 297/423 | 224/423 |
| 数据窃取第 1 步（越权读取）自动放行 | 126/144 | **1/144** |
| 攻击链全程自动放行 | 0/279 | 0/279 |
| 同服务攻击调用自动放行 | 1/19 | 0/19 |

开发集结果的规律相同：正常调用 8/8 放行，攻击调用自动放行从 128/376 降到 4/376，直接拒绝 248/376。

## 4. 解读

1. **P3 本身已经阻止了攻击链全程自动完成**，因为写入和外发都要人工复核。任务对齐的增益在另外两处：
   - **拦下越权读取**：P3 放行所有读取，攻击者可以让模型读出已保存的地址、付款方式、密码库等，读到的数据会进入模型上下文。任务对齐把这类读取从 126/144 降到 1/144。
   - **减少对人工复核的依赖**：198 条攻击调用被直接拒绝，不再交给人。P3.1 的结果表明，如果用户一律批准，危害成功率会从 11.11% 升到 33.33%，所以少让人做决定本身就有价值。
2. **代价**：3/9 条正常调用因为任务里没写服务名而被转为复核：GitHub 仓库任务没提 GitHub，Shopify 任务完全没提服务名，“Teledoc” 是原数据中的拼写错误。按名字匹配服务有这个固有局限，转为复核只是增加摩擦，不会导致危险操作被放行。
3. **漏过的 1 条**：日历任务中出现了“Google”，攻击工具是 `GoogleMapGetCurrentLocation`，规则只用品牌首词判断服务，粒度过粗。另外有 99 条攻击调用使用了开发集没见过的动词（转账、提现、开锁、执行命令、关闭两步验证等），全部按设计退回到 REVIEW，没有被自动放行，但也没有被直接拒绝。

## 5. 局限

- InjecAgent 的攻击大多跨服务，比如读商品时去开智能锁，这对按服务对齐的方法比较有利。同服务子集只有 19 条。
- 攻击调用没有结构化参数，所以无法检验参数来源检查。同工具、不同参数的攻击（比如查询另一个 GitHub 用户）在开发集上漏了 4 条，v1 处理不了。
- 正常调用全部是读取，而且只有 9 条，摩擦的估计误差很大，也没有覆盖用户确实要求写入或发送的场景。
- 只有英文，任务都是单步的。

## 6. 下一步建议

1. 用包含**正常写入任务和结构化参数**的数据（例如 AgentDojo，需要联网下载，需用户同意）检验摩擦和参数来源检查。
2. v2 可以考虑：服务识别用完整服务名代替品牌首词；用 4B 模型或嵌入做服务和动作的语义匹配，以处理没写服务名的任务；加入参数来源检查。任何改动都要另开版本，并在新数据上验证；本测试集已经用过。

复现：`prepare_call_alignment_v1` → `evaluate_call_alignment_v1 --split development` → `--split test`（独占运行目录；测试评估要求代码哈希与开发评分时一致）。
