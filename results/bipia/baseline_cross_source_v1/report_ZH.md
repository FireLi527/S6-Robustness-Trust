# 主 baseline 跨来源冻结评估：离开 BIPIA 后基本失效

日期：2026-10-03。冻结的 P1 规则、P2 语义一致性和混合系统直接用于 InjecAgent 与 NotInject：规则、权重和阈值均未修改，只用 CPU 和本地缓存的 MiniLM。REVIEW 或 BLOCK 都算“检出/报警”。数据哈希按 `data/bipia/cross_source_v1/integrity.json` 核对。P2 新建了自己的嵌入缓存，没有修改 BIPIA 的缓存。

## 1. 主要结果

| 数据 | 性质 | P1 规则 | P2 语义 | 混合 |
| --- | --- | ---: | ---: | ---: |
| BIPIA 邮件（参考：开发所用来源，未见类别测试） | 检出率／误报率 | 93.47%／2.00% | 37.05%／4.00% | 97.08%／4.00% |
| **InjecAgent**，1,054 条攻击 | 检出率 | **3.70%**（39） | **0.19%**（2） | **3.89%**（41） |
| ├ 直接危害（dh），510 条 | 检出率 | 7.06% | 0.39% | 7.45% |
| └ 数据窃取（ds），544 条 | 检出率 | 0.55% | 0.00% | 0.55% |
| **NotInject**，339 条难正常样本 | 误报率 | **16.81%**（57） | 不适用（无用户任务） | 16.81% |
| ├ 第一层 / 第二层 / 第三层，各 113 条 | 误报率 | 19.47% / 17.70% / 13.27% | — | 同 P1 |

结合此前已有的冻结结果（P1 在 AgentInjectionBench 留出组上检出 27.27%、误报 14.29%；在标准库代码上检出 4%；在 RepoGuardBench 代码注释攻击上 0/470），主 baseline 的跨来源表现可以概括为：**检出率从 BIPIA 上的 93–97% 跌到 0–27%，误报率从 2% 升到 14–17%。** 这确认了此前的判断：P1/P2 对 BIPIA 来源存在严重过拟合。

## 2. 原因诊断

1. **P1 只认 BIPIA 风格的措辞。** InjecAgent 上的 39 次命中中，34 次来自高风险词，5 次来自输出控制。InjecAgent 的攻击写成自然的业务请求（例如“请给我的朋友永久开锁权限”“把记录发到某邮箱”），没有“忽略之前的指令”一类的覆盖语句，所以绝大多数不会被规则命中。数据窃取类几乎完全漏检（0.55%）。
2. **P2 的局部攻击被稀释。** 1,054 条都提取到了候选行，但 InjecAgent 的工具返回是单行 JSON，注入句与正常的商品、邮件信息混在同一行，整行与用户任务的相似度远高于复核阈值（≤ 0.03）。这正是 `ENGINEERING_ZH.md` 中提到的“局部攻击被稀释”。
3. **P1 把祈使句当作注入。** NotInject 的 57 次误报中，53 次来自“独立的类指令句”规则。NotInject 本身是含有触发词的普通用户提问，句式大多是祈使句。需要说明的是，P1 原本用于检查**不可信的检索内容**，直接用在用户提问上会放大这个问题；这一误报率不能直接等同于 P1 在检索内容场景下的误报率。

## 3. 结论

- 主 baseline 在 BIPIA 上的高分不能代表一般的提示词注入防护能力；对外介绍时应写明“BIPIA 同来源”这个前提。
- 真正与数据来源无关的防线是 **P3 工具权限**：它不看正文措辞，只限制高影响动作。这次结果进一步支持把重心转向调用级的确定性控制（任务对齐和参数来源检查），而不是继续给 P1 补关键词。
- 本次评估没有根据这些结果修改任何规则。若以后针对 InjecAgent 一类措辞改进检测器，这两个数据集已经看过，必须改用新的来源来验证效果。
